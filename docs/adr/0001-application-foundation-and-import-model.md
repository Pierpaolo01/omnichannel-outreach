# 0001: Application foundation and the import model

Date: 2026-11-12. Status: accepted. Ticket: [#11](https://github.com/Pierpaolo01/omnichannel-outreach/issues/11).

The first ticket lays the foundation later tickets build on. The coordinator set the stack; the implementer added the rest. Each decision says who made it.

## Stack (coordinator)

- TypeScript in strict mode on Node 22, managed with pnpm. `tsconfig.json` adds `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` and `erasableSyntaxOnly`.
- One locally run application. `pnpm dev` starts a single Node HTTP server on 127.0.0.1:4310 that serves the HTTP interface under `/api` and the React single-page app through Vite middleware. `pnpm start` serves the production build from `dist/`.
- SQLite persistence with versioned migrations, behind a module interface. Hosting is deferred: nothing here builds for it or blocks it.
- React, Tailwind CSS v4 and daisyUI 5, themed light and dark from the approved prototype's tokens and typeface.
- Vitest for domain and HTTP behavior, Playwright for browser behavior.
- `pnpm check` runs typecheck, lint, Vitest and Playwright. `.github/workflows/verify.yml` runs it on `pull_request`.

## Choices made by the implementer

- **Node runs TypeScript directly.** Node 22.18+ strips types, so the server, scripts and seed run with plain `node` and no build step. The cost is erasable syntax only (no enums or parameter properties) and `.ts` extensions in imports; `erasableSyntaxOnly` enforces it.
- **SQLite through the built-in `node:sqlite`.** It avoids a native module download. It is still marked experimental in Node 22. Scripts load `src/server/quiet-sqlite-warning.ts` with `node --import`, which drops only the SQLite experimental warning; every other warning still prints. If it changes incompatibly, `src/server/persistence/sqlite-store.ts` and `migrations.ts` are the files to change.
- **Known risk: Node 22's support window.** `engines` pins Node `>=22.18 <23`, and Node 22 leaves LTS at the end of April 2027. Moving to Node 24 is planned before then: re-run `pnpm check`, recheck `node:sqlite`'s API and stability, and widen `engines`.
- **Phone numbers with `libphonenumber-js`** (minimal metadata). Numbers key to E.164 from any written form, using the company's country for national forms, and display grouped for reading and dialing.
- **HTTP with Hono and `@hono/node-server`.** Tests call `app.request()` against a real in-memory SQLite store, so HTTP tests need no network. Request bodies are validated with zod at the edge.
- **Routing with wouter.** Search state on Leads lives in the URL.
- **Playwright 1.64.1**, the release that uses the Chromium build 1248 already in the local cache.
- **Tooling versions** are recent releases the implementer knows well (TypeScript 5.9, Vite 7, Vitest 3.2, ESLint 9) rather than the newest majors.
- **The typeface is self-hosted** from `@fontsource-variable/schibsted-grotesk`, so the local app loads no fonts from Google.

## Module seams

- `src/domain/` holds the rules as deep modules with no I/O. Time and identifiers are passed in.
  - `scraper-export.ts` parses and checks the paired CSV export (verified schema in #11).
  - `import-plan.ts` takes the CRM's directory and one export and returns the full plan: records to write, details to add, enrollments to create and the import summary. It is the seam the enrollment, matching and re-import rules are tested at.
  - `reach.ts` decides which channels a lead can use.
  - `outreach-status.ts` is the closed type of all twelve outreach statuses and their five groups from the spec. Later tickets extend behavior, not the set.
- `src/server/persistence/store.ts` is the persistence interface. Every method is asynchronous, so a hosted adapter (Postgres, D1, libSQL) can satisfy it later without changing callers. The spec needs email and SMS to keep running with the laptop off, so hosting will come within the MVP. An import is one call that loads the directory, runs the plan and applies it in one write transaction, optionally creating the campaign in the same transaction.
- `src/server/app.ts` is the HTTP interface. Tests at this seam cover re-import, multiple campaigns, search and records against real SQLite.
- `src/shared/api.ts` holds the response types the server and the web client share.

## Guardrails

- **Domain code never reads the clock.** An ESLint rule in `eslint.config.js` rejects `new Date()` with no arguments, `Date.now()`, `performance.now()`, `Math.random()`, `randomUUID()`, timers, `node:*` imports and imports from `server/` or `web/` inside `src/domain/`. Later tickets freeze and shorten clocks, so time has to be an input.
- **Prospect records stay out of the repository.** The database lives under `OUTREACH_DATA_DIR`, by default `~/.local/share/omnichannel-outreach` (`$XDG_DATA_HOME` respected). `src/server/config.ts` refuses a data directory inside the repository, and `.gitignore` ignores `*.sqlite*` as well.
- **Development data is separate, and a reset cannot reach real data.** `pnpm dev` and `pnpm seed:dev` use `OUTREACH_DEV_DATA_DIR`, by default `~/.local/share/omnichannel-outreach-dev`. They never read `OUTREACH_DATA_DIR`. Config compares real paths, through symlinks and aliases such as `/tmp` and `/private/tmp`, and refuses a development directory that is, contains or sits inside the app's, whatever variables are set.
- **The local server only answers this machine.** `src/server/guard.ts` accepts only the hosts `localhost` and `127.0.0.1`, which stops DNS rebinding. Routes that change data must carry `application/json` and must not come from another site (`Sec-Fetch-Site`, `Origin`). That stops cross-site forms and no-cors fetches from creating campaigns or leads. The server also refuses to start on a non-loopback `OUTREACH_HOST`: the Host check only defends browsers, and a client on the network could send `Host: 127.0.0.1`. That stays until hosting brings real authentication.
- Fixtures are fictitious. Domains use `.example`, and phone numbers come from the UK's drama ranges (`+44 20 7946 0xxx`, `+44 7700 900xxx`).

## Import model

These rules implement the spec's enrollment section and the principal's decisions recorded on #11. Product rules are cited; matching is a factory choice.

- **Who is enrolled.** Every decision maker with a usable channel is their own lead. A company with no named decision maker is a company lead. When none of a company's decision makers has a usable channel but the company has a shared inbox, the company is enrolled as a company lead through that inbox, and its decision makers stay on the record unenrolled (principal, 12 November 2026). A decision maker with no usable channel is never enrolled.
- **Usable channels.** A decision maker's email and SMS use only their own address and mobile. Calls may use their own numbers or the company main line. A company lead uses the shared inbox and main line. A main line is not treated as an SMS destination.
- **Ownership and identity invariants (coordinator rulings, rounds 2 to 4).** These hold after every import. `src/server/import-sequences.test.ts` checks them on 120 seeded, generated import sequences through the real SQLite store, into two campaigns, with the generator and checks in `test/support/generated-imports.ts`. The generator keeps its own record of the logical people and companies behind every row and, from that record alone, predicts which rows are decisive and which are truly ambiguous. The checks compare the CRM against that record, never against names:
  1. a decisive row is applied, and enrolled when it has a usable channel; an ambiguity the record does not predict fails, and so does a predicted ambiguity that lands in a record;
  2. a row that changed nothing wrote nothing;
  3. every record belongs to exactly one logical person or company, and each logical person or company to one record; a person's record sits at their logical company's record;
  4. nobody holds two enrollments in one campaign, and within a campaign a personal email or mobile is one enrolled lead's and a shared inbox one company lead's;
  5. a contact value has exactly one owner within a company (phones compared by their E.164 key), so a value known as the company's main line or shared inbox is never also a personal detail, and a decision maker's email, SMS and direct-call reach use only their own details;
  6. a bad mark survives every import (tracked by company, channel and value);
  7. importing the same files twice changes nothing;
  8. no import sequence returns a server error;
  9. a contact detail id, once issued, always resolves to exactly one live detail, or is itself live, and that detail is the same address or number: the same channel and key the id had when issued, or the key a number kept by its digits was read to once its company had a two-letter country, held at the same company and never a company's detail resolving to a person's (ticket 12, part 1). The generated test records every detail id it has seen on a page with its value and holder and, after every import, checks that each still resolves through `OutreachStore.contactDetail` to a detail that resolves to itself and has that channel, value and holder, that every detail shown on a page is live, and that no live detail at a company is an unmarked copy of a number marked bad there, read as the phone rule permits. It also fails a seed whose import the store refuses: the store must accept every merge the planner asks for.

  `src/server/import-sequences-oracle.test.ts` replaces the matcher with one that refuses every row and checks that the sequences then fail. `src/server/import-sequences-merge-mutation.test.ts` runs every seed against three broken stores and checks that invariant 9 fails for each: one deletes merged rows after each import, as the store did before migration 4; one points every merged row at a live detail with another key; one points it at the same number held by another company. The generator only writes input the rule can decide: same-name colleagues first appear together, an ID is never reused by someone whose namesake has carried it onto a record, a same-name colleague lists only their own email and numbers, and every company row carries its anchor (a place_id, main line or address) unless the company never has one. It does generate blank IDs, IDs reused by a different person or company, same-name colleagues, companies with blank identity fields, duplicate rows, a second campaign and bad marks. In the first import only, a company not known by its main line alone may have no country: its national numbers are then kept as their digits, and a later row with a country reads them once. The population also has a company that never carries a two-letter country, whose rows list a UK, a US or a +800 main line, sometimes two in one file with their own IDs and one place, and whose two people list those lines in national and international form; Northgate's rows sometimes list a US line. Across 120 seeds, companies with no country hold lines from two or more origins in 95 (all three in 34), their people hold numbers kept as digits in 85, and 8 merge a detail (all phones; no generated sequence merges an email, which needs two people at one company holding one address, and the population has none). The model reads each generated number as the rule permits, never as British by default: written internationally, as that number; at a company with a two-letter country, as the number the generator meant in that number's own region; otherwise as its digits. The ownership check treats a number shown by its digits as a different number, as the rule does, and a bad mark on one is checked by resolving the marked detail's id. A failure it finds is shrunk into a named regression in `src/domain/import-matching.test.ts`, which runs through the real store.

  **Known limits of the generator** (reviews and verification, round 4). It does not reach: a namesake arriving after the other already has a record; a company losing its last anchor, or being renamed or moving while its anchors change; names that change beyond accents, case, titles and punctuation; duplicate rows that are not exact copies; a main line shared by two companies; a person changing company; arbitrary populations (its people, companies, titles and pools are fixed, and rows are not shuffled); databases with duplicate copies left by older versions; enrollment progress beyond queued; concurrency, crashes during a write or I/O failure; and two-letter countries other than Great Britain. Named regressions cover the first five where the rule decides them; `src/domain/import-regions.test.ts` covers US, GB and FR line histories and every review sequence of round 4.
- **Personal versus company details.** When a number or an email becomes known as a company detail (main line or shared inbox), every personal copy at that company folds into the one company detail. The first copy moves and keeps its id, in a fixed order (copies stored before the import first, then by their holder's normalised rows, never by record or row order); further copies merge into it; a bad mark on any of them survives. See "Merged contact details" for what a merge keeps. A company's details listed against a person are never stored as theirs. Whether an address is a company's shared address is decided by the Businesses file listing it for that company (in this import or in a row applied before), not by whether the company ended up storing it, so an inbox the equal-claims rule stores on no company is still nobody's personal email (round 9). One rule covers a copy a person already holds (round 10): when a company's rows list an address as shared, every personal copy of it held by that company's people stops being a personal detail. If the company stores the inbox, the copy moves to it; if the equal-claims rule leaves it stored on no company, the copy stays on the person flagged `listed_shared` (migration 3), keeping its bad mark, but gives no reach, is no destination and is not shown. A company and its own people never block each other, and a person whose own company lists an address never blocks another company with it. Main lines are not reserved destinations, so every company that lists one stores it and takes its people's copies. A number or address a colleague at the same company held before this import stays the colleague's, and the row that listed it says so in its result. A personal detail two people newly list in one import is an equal claim and goes to the equal-claims rule below, never to whichever row comes first. `dial_phone` is a mobile only when `dial_phone_type` says mobile or cell. A number listed both as direct and as mobile is a mobile, and a direct number a later import shows to be a mobile becomes one (the lead counts as updated). The real sample has no values in these fields, so the type mapping is an assumption to revisit when real values appear.
- **Phone identity (review round 4).** A number has one key however it is written, and is read by one rule wherever the import keys or compares a number, including company matching, grouping within a file and stored row identities (`readNumber`, `rereadNumbers` and `readMainLine` in `src/domain/`): a number written in international form (`+` or `00`) is that number, and the `phone_e164` cell is international by definition, so it is read as international first, whatever the company's country, even without its plus sign when it is valid that way (review round 5); otherwise, if the company has a two-letter `country` (all 12 real rows do), the number is read in that country; otherwise it is not interpreted: it is kept as its digits exactly as written and keyed by them, never matched to an international number, never a mobile for SMS (a mobile so kept is stored as a direct number), and shown as its digits so it can still be dialled by hand. A region is never inferred from a company's main lines: that was a guess, against the import's settled principle of no guessing, and every phone defect of four review rounds came from it. Reading is one-way. When a company that had no two-letter country gains one, every number it and its people hold by their digits is read once in it, before the import adds any detail, and every live copy at the company that is then one number folds into one detail: the company's own if it holds one, else a copy already read, else by holder and as written; earlier ids resolve to it and it is bad if any copy was. A later row that names the country without a two-letter code never replaces one, so a reading never goes back to digits. `0044` prefixes are understood, and search finds a number typed in international or national form.
- **Joining the two files (coordinator ruling, round 1).** A People row joins only to a business in the same export. There is no fallback to a company already in the CRM, and a blank `business_id` never matches. Such a row is not enrolled, with the reason that its company is not in the Businesses file.
- **Matching (coordinator ruling, round 3: no guessing).** Scraper IDs are not proven stable across runs, so matching rests on evidence, implemented once in `src/domain/matching.ts` for both companies and people.
  - **Provenance (coordinator ruling, round 7).** Every row applied to a company or person leaves its normalised identity on that record (`row_identities`, migration 2): the row's IDs, name, contact details and other fields, normalised exactly as "identical after normalising" is below. On a later import, a row whose normalised identity is stored on exactly one record resolves to that record before any evidence is weighed, and the rows collapsed with it go with it if their own evidence points there too. Towards other rows it weighs only what its own evidence weighs, so contests settle as on the import that applied it, and its record is no longer anyone else's by name alone. Rows that leave a collapsed group together and resolve the same way on their own stay together. An unchanged row can therefore never become a new record or move, whatever the rules below do with new or changed rows, and importing the same files again changes nothing. Rows that are new or changed since they were last applied go through the rules below unchanged.
  - **A scraper ID repeated with a conflicting identity inside one file is bad input (coordinator ruling, round 8).** Before matching, each file is checked: one non-blank person ID (within one business) on rows whose names disagree, or one non-blank business ID on rows whose names disagree or whose place IDs differ, makes all of those rows bad input. They change nothing, nor do the People rows of a refused business row, and the results list each with a plain reason ("its person ID is on more than one row of this file with different names"). A blank name or place ID disagrees with nothing, and rows that share an ID and agree are true duplicates and collapse. Matching therefore never has to decide between rows that share an ID but claim different identities.
  - **One evidence standard in a file and across imports.** A shared ID joins rows of one file only when their names agree (the rest is bad input, above), exactly as an ID counts across imports only with an agreeing name. A blank name agrees with any name in both places, but across imports its ID evidence weighs less than a name that agrees. The one deliberate difference: in a file, rows identical after normalising, or with the same personal email, or with an agreeing name and the same personal number, are collapsed before matching because they are copies of one row; across imports the same evidence reaches the same record through the matching tiers. Within a file a shared personal email or place ID is decisive, so a row tied to its group that way stays with it; only rows held in by weaker keys are checked on their own. Provenance keeps either path from changing a repeat import.
  - **Rows that are one person or company are collapsed first.** Business rows with the same non-blank `business_id` or `place_id` and an agreeing name, or identical after normalising, are one company, and so are rows with an agreeing name and main line whose addresses do not differ. At one company, People rows with the same non-blank `person_id` and an agreeing name, the same personal email, or identical after normalising, are one person, and so are rows with an agreeing name and the same personal number. Rows that carry different decisive identities are never collapsed: two `place_id`s, or two personal emails already on record for different people. The rows of each identity stay together, and rows with neither are grouped among themselves. A People row whose `business_id` is on business rows of two companies changes nothing. After matching, each row of a collapsed group is decided on its own evidence, name agreement included, beside the file's other groups: a row whose own evidence points to another record, or contradicts itself, leaves the group and is settled exactly as if it were imported alone, and People rows whose `business_id` then sits on rows of two companies change nothing. A row with no evidence of its own stays: it is a copy of the others (rounds 5 to 8). Rows that differ in anything else, same-name colleagues included, stay separate.
  - **A row matches a record that existed before this import only on evidence that singles it out.** Company evidence, strongest first: the same `place_id`; one of its `business_id`s with an agreeing name and, where both sides have them, an agreeing main line or address (street with postal code); an agreeing name and a main line the row carries; an agreeing name and address; an agreeing name alone, when the row has no `place_id`, main line or address. A company with a different `place_id` is never a candidate. Main lines compare by their E.164 key; one stored before its company's country was known is read again in the row's country first, so the company is still found and the line keeps its bad mark. Person evidence, at the row's company, strongest first: one of the row's personal emails; one of its `person_id`s with an agreeing name; an agreeing name and a personal number the row carries; an agreeing name alone.
  - **How the evidence decides.** The strongest kind of evidence that points anywhere decides. A `place_id` or a personal email decides alone, and when it points to several records nothing weaker chooses between them. After any other kind, every other kind that points anywhere must agree: it narrows the candidates, and evidence that points only to a different record is a contradiction. A main line on record is also checked whatever the row's name: when it belongs to a company the row's other evidence does not point to, or to a company with a different name and nothing else points anywhere, that is a contradiction, not a new company. An address alone is not checked this way, because different businesses share buildings. A name alone is tried last, only for rows with no other evidence, and never points to a record another row of the same export points to: rows the import keeps apart are different people or companies.
  - **No change on ambiguity.** When several records fit a row and nothing in it singles one out, when its details contradict each other or a record on file, or when the one record that fits also fits another row of the export, the row changes nothing: no new record, no enrollment, no detail change. When one record is fitted by several rows, the row with the strongest evidence takes it if it is alone in that; the others change nothing. A People row whose company row changed nothing changes nothing either. Each such row is reported as not matched, with its title, its row number in the file and a plain reason that says, for a contradiction, which details disagree.
  - **Never evidence:** creation order, row order, or an identifier made up from a name.
  - **Names** compare after removing accents, case and titles such as Dr, Mrs, Prof and PhD. Punctuation and spacing are dropped rather than treated as word breaks, so "Dr. Grace Okafor" matches "Grace Okafor", and "O'Neil" matches "ONeil".
  - **Declined (coordinator ruling):** an email match is not refused for an unrelated name, and no single "newest" detail is chosen.
  - **Each row's record is reported.** The import summary lists, for every row of both files, the company or person record it landed in, or nothing. The generated test uses it to check identity; nothing else reads it yet.
- **Re-import.** Existing enrollments are never touched, so no sequence restarts. New details are added alongside old ones. A detail counts as newer when its owner already had a detail on the same channel from an earlier import. Bad marks are never cleared. Non-contact fields such as a title take the newest non-empty value.
- **Safety net (coordinator ruling, round 4; order-free since round 7).** Whatever matching decides, within one campaign a personal email or mobile belongs to at most one enrolled lead, and a shared inbox to at most one company lead. Calls through a shared main line are not affected. Enrollments are decided after every lead of the import is known. One address is one mailbox: a person's email and a company's shared inbox are reserved by address alike, so a company that only now lists someone's address cannot get it in a campaign that person is in (round 10; mobiles have no such split, since a company lead has no SMS). Each destination goes to the lead with the strongest claim: enrolled in the campaign and holding it or listing it (in this import's rows or in its provenance); holding it from before this import; holding it from this import; only listing it in its row. A strictly stronger claim always wins; the others are not enrolled, and the row says whose the destination is and whether that lead is enrolled. A lead never gains such a destination while another lead in one of its campaigns has it. The planner enforces this using every campaign's enrollments; the store checks the stored destinations again inside the import transaction and keeps nothing of an import that would break it.
- **Equal claims (with the principal, 13 November 2026).** When leads with equally strong new claims contest one detail, `settleEqualClaims` in `src/domain/import-plan.ts` decides, and it is the only place that does: for colleagues storing a personal detail and for leads being enrolled with a destination. Its claimants are ordered by their rows' normalised identities, not by record IDs (new records receive IDs in row order), so a rule that picks one never depends on row order. Today it gives the detail to nobody: neither colleague stores it, and none of the tied leads is enrolled with it, each naming the others without calling them enrolled. The principal is expected to choose "enroll both, use the shared detail for one"; that change is made in that function alone.
- **Merged contact details (ticket 12, part 1; migration 4).** When the import finds that two stored details are one (`DetailConsolidation`, a personal copy folding into a company detail), the absorbed detail keeps its row, id, owner, value and bad mark, and records the detail it was merged into in `merged_into`. A live detail is one with `merged_into` null, defined once by the `live_contact_details` view (migration 5), and every reader reads that view: the directory the planner matches and claims against, reach, the campaign safety net, search, the person and company pages and their counts. So everything behaves exactly as when the row was deleted. The store merges only one detail held twice: both live, the same channel, held at one company and never a company's detail into a person's, with the key the plan's consolidation carries and, for a copy kept by its digits, the country the plan read it in, which the store checks exactly and never derives for itself: the target holds that key, and the copy holds it too or reads as it in that country. Any other merge is refused and the import keeps nothing. A bad mark on the copy is copied to its target, so a bad mark on either survives. One owner, channel and key is unique among live details only, so an absorbed row never blocks its old owner from holding that value again. `OutreachStore.contactDetail(id)` resolves any issued id to the live detail at the end of its chain, however long; the recursive query keeps each id once, so a cycle, which these merges cannot make, would still end. Chains are kept, not flattened, so each row records its own merge. `markContactDetailBad` marks the live detail the id resolves to. Sends, delivery results and activity can therefore store detail ids and resolve them later.
- **Row order never changes the outcome.** Every rule above is evaluated on the whole file. Where several rows land on one record, their fields and the spelling of each detail they store are merged in a fixed order, by normalised row identity, not by position. A record a repeat import leaves as it was is not written again, so its modification time stays. `src/server/import-sequences.test.ts` imports every generated file a second time with its rows shuffled and requires an identical CRM and identical counts after every import.
- **Databases from before migration 2** have no provenance. None holds real data. Importing into one that already holds people is refused with a message to recreate it (delete it, or run `pnpm seed:dev`), rather than risk duplicating people; no backfill is attempted.
- **Summary.** Every row of the export lands in exactly one outcome. New means enrolled now. Already enrolled means no new contact details. Updated means already enrolled, and the import brought newer contact details. Not enrolled carries its reason: no usable channel, a destination another enrolled lead already has, a People row whose company is not in the Businesses file, or a row that could not be matched safely and so changed nothing. That last one is labelled "Not matched", because the person may well be enrolled already, and the summary says anyone already enrolled carries on. The last two are rows, not a failed import.
- **Rejected files.** A file missing required columns, a file in the wrong slot, or a pair in which no person belongs to any business imports nothing. When it comes with a new campaign, the campaign is not created either. Extra columns are ignored.
- **No exclusions.** Only the target campaign's enrollments are consulted. Other campaigns never exclude anyone.
- **Context is kept.** Each company and person stores the full source row of its latest import, so the social URLs and scraper evidence that later tickets need are not lost.
- `email_status` from the scraper is stored in the source row but not interpreted.

## Known limits (review round 8, not addressed)

- An enrolled lead's claims derived from its stored rows never expire: once an old row listed a mobile, that mobile keeps blocking its holder in the lead's campaigns even after exports stop listing it, and the reason then names the lister. Conservative, never wrong outreach.
- `row_identities` has no foreign key, so deleting or erasing a record must delete its identities too when those features arrive.
- `listedDestinations` and `sharedAddresses` read the stored identity by position; version the identity's shape before changing it, so an old identity is never misread as an email or a mobile.
- A company whose two-letter country changes to another keeps its earlier readings, so a repeated row whose national number does not read in the new country can add an unmarked digits copy beside a number marked bad (review round 5; the integration branch behaves the same).
- A company with no country whose main line is written in national form cannot be matched by that line, so a later row spelling it internationally, with no other evidence, can create a second company (review round 5).
- The generated test's model accepts a number's countried reading even at a company that has no country, so it would not notice such a number being read there (review round 5).

## Constraints for later tickets

- **Reference contact details by id and resolve them.** A detail id stored by a send, delivery result or activity may later belong to a detail merged into another. Resolve it through the store's resolution: `OutreachStore.contactDetail` from outside the store, or the same resolution query inside a store transaction (a claim or handover), which follows the chain to the live detail. Anything new that reads contact details reads `live_contact_details`.
- **Rebuilding the contact-details table.** A migration that rebuilds `contact_details` the way migration 4 does must drop the `live_contact_details` view first and recreate it afterwards; SQLite refuses to rename a table under a view that names it.
- **A company lead outlives a newly reachable decision maker.** When a later import makes one of a company lead's decision makers reachable, that person is enrolled and the company lead carries on. Whether the company lead should end then is with the principal. The company record says what is true now in either case.
